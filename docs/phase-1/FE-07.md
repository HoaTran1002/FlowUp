# FE-07 — Deliveries List, Detail and Attempt Timeline

**Task (`IMPLEMENTATION_PLAN.md` §4):** deliveries list/detail, attempt timeline, status/next-retry/errors.
**Dependencies:** `BE-11`, `FE-04`, `FE-06`.
**Requirements:** `UI-08`, `UI-09`, `FR-OBS-02`..`04`. Tests: `UX-AC-05`, `UX-AC-09`, `QA-E2E-04`, `QA-E2E-12`, `QA-UI-03`, `QA-UI-06`, `AT-12`.

**Normative inputs:** `UI_UX_SPECIFICATION.md` §3 UI-08/UI-09, the terminology subsection, §4.3 wireframe, §5; `API_SPECIFICATION.md` §5; `PRD.md` §6 status definitions; `DATABASE_DESIGN.md` §4 state machines.

## Scope boundary

In scope: `/app/deliveries` list with filters and cursor pagination, and `/app/deliveries/:deliveryId` detail with the snapshotted destination, generation, safe last error and the per-attempt timeline.

Out of scope: the replay action (`FE-08` — this task renders the delivery state replay depends on), events (`FE-06`).

## Implementation requirements

1. **List (`UI-08`).** Status, endpoint, application, event ID, attempt count, next retry and time filters, through `GET /v1/deliveries`. Filter by application, endpoint, status, event and date (`FR-OBS-02`), with cursor pagination and persisted search parameters (`UX-AC-09`).
2. **Status vocabulary — render exactly these meanings** (`UI_UX_SPECIFICATION.md` §3 terminology):
   - `PENDING` awaiting attempt · `IN_PROGRESS` worker leased · `RETRY_WAIT` next retry scheduled · `SUCCEEDED` transport `2xx` · `FAILED` terminal error or exhausted retry · `CANCELLED` no further attempt.
   - "Pending" is never "delivered". `SUCCEEDED` means transport acknowledgement, not consumer business completion (`FR-DEL-05`).
3. **A failed attempt is not a failed delivery.** The list and detail must distinguish the delivery's status from an individual attempt's outcome, and show attempt number, next retry time and generation so a retrying delivery is not read as final (`apps/web/AGENTS.md` §5).
4. **Independence (`UX-AC-05`).** Two deliveries of one event display separate statuses and separate timelines; one endpoint's failure must never visually contaminate the other (`FR-DEL-06`, `QA-E2E-04`).
5. **Detail (`UI-09`).** Status, snapshotted destination shown according to permissions and labelled as a snapshot, generation, attempt count, safe last error code, next retry time, and links to the event. Follow the §4.3 wireframe's information order.
6. **Attempt timeline.** From `GET /v1/deliveries/{id}/attempts`: generation, attempt number, started time, HTTP status where present, safe error code and duration. Order must be consistent across generations, and replay history must remain visible rather than being replaced (`QA-UI-06`, `FR-OBS-04`).
7. **UNKNOWN attempts.** Render `UNKNOWN` as a distinct outcome with an explanation that the result could not be determined. Never present it as a confirmed failure or success (`UI_UX_SPECIFICATION.md` §3, `QA-UI-06`, `NFR-03`).
8. **Safe errors only.** Display the server's error category. Never render a raw downstream response body, a signature or a secret — the API does not return them, and the UI must not reconstruct or request them (`FR-OBS-05`).
9. **Polling.** Polling is permitted only for non-terminal states (`PENDING`, `IN_PROGRESS`, `RETRY_WAIT`), with a bounded interval and cleanup on unmount; stop when the delivery reaches a terminal state. No WebSockets or SSE without a documented requirement (`apps/web/AGENTS.md` §6).
10. **Server-derived state.** Never show an optimistic success. Delivery state comes from the API; the UI asserts nothing about delivery it has not been told (`apps/web/AGENTS.md` §6).
11. **Accessibility and layout.** Stable columns, responsive overflow, truncation with tooltips for long IDs and URLs, no layout shift on filter or sort, status by text and icon rather than colour alone (`QA-UI-03`, `QA-UI-04`).

## Acceptance criteria

| # | Criterion | Test |
|---|---|---|
| 1 | Endpoint A succeeded and endpoint B failed for one event display separate statuses and timelines | `UX-AC-05`, `QA-E2E-04` |
| 2 | A retrying delivery shows attempt number and next retry, and is not labelled final | `FR-OBS-04` |
| 3 | `UNKNOWN` attempts are described distinctly and never as a confirmed failure | `QA-UI-06` |
| 4 | Attempt order stays consistent across generations and prior-generation history remains visible | `QA-UI-06`, `FR-REP-02` |
| 5 | The destination is labelled as the acceptance-time snapshot | `FR-END-01` |
| 6 | No raw response body, signature or secret is rendered | `FR-OBS-05`, `QA-SEC-07` |
| 7 | Cursor paging and filters behave correctly and persist | `QA-E2E-12`, `UX-AC-09` |
| 8 | Polling runs only for non-terminal states and stops on unmount and on terminal state | `apps/web/AGENTS.md` §6 |
| 9 | "Pending" is never shown as "delivered"; `SUCCEEDED` is labelled as transport acknowledgement | `QA-UI-03` |
| 10 | A developer can diagnose the most recent failure and read its attempt history | `AT-12` |

## Tests

- **Unit:** status label mapping for all six delivery states and all four attempt outcomes; next-retry formatting; polling predicate and teardown.
- **Component:** list states; detail with a multi-generation timeline fixture; an `UNKNOWN` attempt fixture; two deliveries of one event with divergent outcomes.
- **Integration (mocked API):** paging and filters; polling a `RETRY_WAIT` delivery to a terminal state and stopping; `404` path.

## Definition of Done

List and detail implemented against the contract; every delivery status and attempt outcome rendered with the exact documented meaning; attempt versus delivery distinction clear; `UNKNOWN` honest; independence across endpoints preserved; destination labelled as a snapshot; no unsafe content rendered; bounded polling with cleanup; accessibility met; listed tests pass.
