# FE-10 — Browser E2E, Documentation Examples and Secret Hardening

**Task (`IMPLEMENTATION_PLAN.md` §4):** browser E2E tests + documentation examples + secret safety hardening.
**Dependencies:** `FE-02`..`FE-09`, `BE-14`.
**Requirements:** `UX-AC-01`..`UX-AC-10`. Tests: the full `QA-UI-*` set, `QA-SEC-07`, `QA-E2E-01`..`12` from the browser where applicable.

**Normative inputs:** `UI_UX_SPECIFICATION.md` §6 (UI acceptance criteria); `TEST_PLAN.md` §1, §2, §5, §6; `IMPLEMENTATION_PLAN.md` §7 (pilot acceptance scenario); `apps/web/AGENTS.md` §8.

This is the frontend's release gate. It proves the pilot workflow in a real browser against real services.

## Scope boundary

In scope: the browser E2E suite, the user-facing documentation examples, and a final secret-exposure audit across the whole frontend.

Out of scope: new features or screens. If E2E reveals a defect, fix it in the owning task's code and say so; do not paper over it in the test.

## Implementation requirements

1. **Environment** (`TEST_PLAN.md` §2). Run against API, dispatcher, worker, PostgreSQL, Redis and **two deterministic HTTPS receiver simulators** supporting `2xx`, `4xx`, `429`, `5xx`, delayed, hung and disconnect responses. Verify signatures from the raw received body. Use controlled DNS and egress fixtures for SSRF cases — never attempt to reach real internal infrastructure (`TEST_PLAN.md` §9).
2. **Pilot acceptance scenario** (`IMPLEMENTATION_PLAN.md` §7). Drive end to end in the browser: admin signs in; creates an application and a scoped publishing key; configures two HTTPS endpoints subscribed to `order.created` and stores both secrets once; a producer publishes with an idempotency key; A returns `2xx` while B returns `503` then `2xx`; the dashboard shows one event, two independent deliveries and every attempt; the same key republished changes nothing while conflicting content returns `409`; B is failed permanently in a second run and replayed after restoration, showing a new generation with history intact; a disabled endpoint receives no new attempt; cross-organization data is inaccessible; a private-IP target is rejected.
3. **UX acceptance coverage.** One test per criterion, `UX-AC-01`..`UX-AC-10`, asserting the user-visible outcome rather than internal state:
   `01` create application and endpoint with the one-time secret modal · `02` secret unavailable after refresh · `03` Developer denied `/api-keys` with no metadata · `04` accepted event with no subscribers · `05` A succeeded while B failed, separately · `06` replay warns, returns `202`, preserves history, increments generation · `07` replay raced or double-clicked shows `409` or the prior generation with no fake success · `08` endpoint disable warns about pending and in-flight work · `09` pagination and filters stay consistent · `10` rate limit, error and session expiry recover correctly.
4. **Secret hardening audit** (`QA-SEC-07`, `apps/web/AGENTS.md` §4/§8). Prove, mechanically where possible, that after a creation or rotation flow no raw API key or signing secret exists in: the DOM after dialog close, `localStorage`, `sessionStorage`, IndexedDB, cookies, the TanStack Query cache, any persister, the URL or history, console output, analytics or error-report payloads, network request headers from the dashboard, or any test artifact or screenshot. Also assert no dashboard request ever carries a `flw_` credential.
5. **Artifact hygiene.** Do not snapshot full keys, signatures, private payloads or customer data. Screenshots and traces must be reviewed for credential exposure before being stored; failing-test artifacts are subject to the same rule (`apps/web/AGENTS.md` §8).
6. **Documentation examples.** Publish user-facing examples consistent with `BE-14`: the producer publish request with an obviously fake key, stating that `202` means accepted and not delivered; the consumer verification guidance pointing at `BE-14`'s raw-byte verifier with its freshness window and constant-time comparison; and an explicit statement that delivery is at-least-once, so replay and retry can deliver the same event more than once and consumers must deduplicate by `FlowUp-Delivery-Id` or `FlowUp-Event-Id`.
7. **No security claim from the UI.** Nothing in this suite may be presented as proving server-side authorization. Hiding a control is not enforcement; the authorization assertions live in the backend suites and are cited, not re-claimed (`apps/web/AGENTS.md` §8).
8. **CI integration.** Add `test:e2e` to the root scripts and to CI with deterministic fixtures, a reset database and Redis between suites, and a deterministic clock where retry timing is asserted (`TEST_PLAN.md` §2). The suite must be stable, not flaky-tolerated; quarantine with a tracked reason rather than a retry loop.

## Tests

This task **is** the test deliverable. Beyond the above: a negative test that a tampered or stale signature fails the documented verifier, and a cross-tenant navigation test confirming Org A cannot reach Org B data from the browser (`QA-AUTH-02`).

## Definition of Done

The pilot workflow passes end to end in a browser against real services with deterministic receivers; every `UX-AC` criterion has a passing test; the secret-exposure audit is clean and mechanically asserted; documentation examples are accurate and honest about at-least-once delivery; artifacts are credential-free; `test:e2e` runs in CI and is stable; any defect found was fixed in its owning task and reported, not worked around in the test. Report explicitly which `QA-*` cases were executed, which were not, and why.
