# BE-01 — Workspace, Processes and Infrastructure Bootstrap

**Task (`IMPLEMENTATION_PLAN.md` §3):** Bootstrap Bun workspace, NestJS config, logging/request IDs, Prisma, Postgres/Redis Compose, CI.
**Dependencies:** none.
**Acceptance:** app health in Compose; tests and migrations run via CI.
**Requirements:** `NFR-07`. Supporting: `SYSTEM_ARCHITECTURE.md` §3, §7; `TECHNICAL_DESIGN.md` §1, §2, §9, §10; `DATABASE_DESIGN.md` §8.

**Prerequisites:** read `AGENT_ADAPTER.md`, root `AGENTS.md`, `apps/api/AGENTS.md`, and `README.md` §4–§8 of this folder. Do not start without them.

## 2. Step 1 — Workspace root (D1)

1. Initialize the Bun workspace with members `apps/*` and `packages/*`.
2. Add the root scripts listed in `README.md` §6.1. CI and every later task report reference these names.
3. Add `tsconfig.base.json` with `strict: true`; each workspace extends it and sets its own `outDir`/`rootDir`.
4. Add ESLint and Prettier with one shared base config. Enforce: no floating promises, explicit module boundaries, no default exports in backend modules (consistency), no `console.*` in application code (use the logger).
5. Add `.gitignore` (`.env`, `node_modules`, `dist`, Prisma generated client), `.editorconfig`, and a committed `.env.example` holding the variable names from `README.md` §7 with **placeholder, non-secret** values.

**Verify:** `bun install` succeeds on a clean checkout; `typecheck`, `lint`, `test` all run (tests may be trivially empty at this step).

## 3. Step 2 — Shared configuration and telemetry (D2, D9)

### 3.1 Env schema — fail fast

In `packages/config`, define one Zod schema per process role (api, dispatcher, worker) over the variables in `README.md` §7. Required behavior (`TECHNICAL_DESIGN.md` §10):

- Parse once at bootstrap; on failure, log the **names** of the invalid variables and exit non-zero.
- Never log a variable's value. `DATABASE_URL`, `REDIS_URL` and `SECRET_ENCRYPTION_KEY` are secret-bearing.
- Validate `SECRET_ENCRYPTION_KEY` presence and decoded length only. Phase 1 does not use it.
- Expose a typed, frozen config object through NestJS DI. No direct `process.env` reads outside this package.

### 3.2 Structured logging

Per `SYSTEM_ARCHITECTURE.md` §7, logs must be structured and carry: `request_id`, `organization_id`, `event_id`, `delivery_id`, `attempt_id`, `generation`, `worker_id`, sanitized error category, trace ID. In phase 1 only `request_id`, `worker_id`/process name and trace ID exist; the field contract must already be in place so later tasks only populate it.

Required:

- One logger provider shared by all three processes; JSON output in non-development.
- Correlation ID middleware/interceptor in `apps/api`: accept an inbound request ID header if present and well-formed, otherwise generate one; attach it to the request-scoped log context and echo it in the response.
- The `request_id` emitted in logs must be the same value returned in the API error envelope (`API_SPECIFICATION.md` §1), so phase 1 fixes its generation and format now.
- A redaction layer: `authorization`, `cookie`, `set-cookie`, `flowup-signature`, `idempotency-key` values, request/response bodies, and any field named like a secret must never be serialized. Add a unit test asserting a log record built from a request carrying `Authorization: Bearer flw_test...` contains no part of that value.

### 3.3 Contracts package (D3)

Create `packages/contracts` exporting, for phase 1, only: the error envelope type, the cursor-pagination envelope type (`{ data, next_cursor }`), and the health/readiness response types — all exactly as `API_SPECIFICATION.md` §1 defines them. These are the first shared types the frontend consumes; do not add business DTOs yet.

**Verify:** process exits non-zero with a missing variable; redaction unit test passes; `packages/contracts` builds and is importable from both `apps/api` and `apps/web`.

## 4. Step 3 — Prisma and PostgreSQL (D7)

Per `TECHNICAL_DESIGN.md` §2, migrations are centralized, not per executable.

1. Place `schema.prisma` at `prisma/schema.prisma`; all three backend apps use the single generated client.
2. Phase-1 schema content: datasource, generator, and **no business models**. To prove the migration pipeline, add one infrastructure-only model that later tasks keep — a schema metadata/health table is acceptable — or generate an empty baseline migration. Do not pre-create `organization`, `event`, `delivery`, `outbox_message` or any other table from `DATABASE_DESIGN.md` §3; that is `BE-03`, which follows the migration sequence in `DATABASE_DESIGN.md` §8.
3. Create `infrastructure/migrations/` for the raw SQL that Prisma cannot express (partial indexes, locking helpers per `DATABASE_DESIGN.md` §6). Leave it empty with a README explaining when to use it.
4. Wire `db:generate`, `db:migrate`, `db:migrate:deploy`.
5. Set a per-process connection pool from `DATABASE_POOL_SIZE`; api, dispatcher and worker size independently (`TECHNICAL_DESIGN.md` §10).

**Verify:** `db:migrate` applies cleanly to a fresh Compose database; re-running is a no-op; `db:migrate:deploy` works in CI against a service container.

## 5. Step 4 — Redis and BullMQ connectivity

Phase 1 proves connectivity only. No queue semantics, no retry configuration, no processors.

1. A shared BullMQ connection factory in `packages/config` reading `REDIS_URL`.
2. Readiness in dispatcher and worker includes a Redis ping.
3. Record in code comments or the module docstring the two settled constraints so later tasks do not re-litigate them: Redis is execution coordination only and never the authoritative record (`SYSTEM_ARCHITECTURE.md` §3), and v0.1 uses `attempts: 1` per job with the database owning the retry schedule (`TECHNICAL_DESIGN.md` §4, `apps/api/AGENTS.md` §5).

**Verify:** a throwaway integration test enqueues and consumes one trivial job against Compose Redis, then is either kept as a connectivity smoke test or removed — do not leave a half-built delivery queue behind.

## 6. Step 5 — Three processes (D4, D5, D6)

Per `SYSTEM_ARCHITECTURE.md` §3, one codebase, three separately runnable processes.

### 6.1 `apps/api`

- NestJS HTTP app, global validation pipe (`whitelist`, `forbidNonWhitelisted`, transform) so later DTOs are validated at the boundary by default.
- Global exception filter emitting the error envelope from `API_SPECIFICATION.md` §1: `{ error: { code, message, request_id, details } }`, with no payloads, secrets, stack traces or downstream bodies. Phase 1 covers `400`, `401`, `403`, `404`, `409`, `413`, `422`, `429`, `5xx` shapes even though no business route emits them yet.
- Body size limit configured now, aligned with the ≤256 KiB payload proposal (`ARCHITECTURE` §8, `ADR-04` pending) so `413` is produced by configuration rather than ad hoc code. Record that the exact limit is ADR-04-dependent.
- Routes: `GET /health` (liveness: process is up) and `GET /ready` (readiness: PostgreSQL reachable, Redis reachable, migrations applied). Keep these **outside** `/v1`; they are not part of the public API contract.
- **No authentication implementation.** If a guard placeholder is needed to keep the router honest, it must deny every request and be clearly marked as blocked by ADR-01.

### 6.2 `apps/dispatcher`

NestJS application context (not an HTTP server) that boots, validates config, connects to PostgreSQL and Redis, exposes health/readiness (minimal HTTP listener or a documented equivalent probe), logs startup with its process identity, and shuts down gracefully. **No outbox polling loop** — that is `BE-08`.

### 6.3 `apps/worker`

NestJS application context that boots, validates config, connects to PostgreSQL and Redis, exposes health/readiness, reads `WORKER_CONCURRENCY` without yet consuming jobs, and shuts down gracefully. **No HTTP egress client, no signing, no SSRF validator, no processor** — those are `BE-09`.

### 6.4 Graceful shutdown (all three)

Per `TECHNICAL_DESIGN.md` §10: on `SIGTERM`/`SIGINT`, stop accepting new work, drain in-flight work within a bounded deadline, close Prisma and Redis connections, exit zero. Phase 1 establishes the hook; later tasks add "leave leases recoverable".

**Verify:** each process starts and answers both probes; each exits zero on `SIGTERM`; readiness turns unhealthy when PostgreSQL or Redis is stopped.

## 7. Step 6 — Docker Compose (D8)

Per `SYSTEM_ARCHITECTURE.md` §3, distinct containers: `api`, `dispatcher`, `worker`, `postgres`, `redis` (`web` is covered in `FE-01.md`).

Required configuration:

- **postgres:** pinned version, named volume, healthcheck, local-only credentials from `.env`.
- **redis:** pinned version, **`maxmemory-policy noeviction`** (`SYSTEM_ARCHITECTURE.md` §3 — non-negotiable; eviction would drop coordination state), persistence enabled, healthcheck.
- **api / dispatcher / worker:** depend on both healthchecks, read the same `.env`, run as a non-root user, each with its own healthcheck pointing at its readiness probe.
- No service publishes a port it does not need; no container runs privileged.

**Verify:** `compose:up` reaches healthy for all five services from a clean volume; `CONFIG GET maxmemory-policy` returns `noeviction`; stopping `redis` degrades dispatcher/worker readiness without crash-looping the API.

## 8. Step 7 — Testing baseline

Set up the layers `TECHNICAL_DESIGN.md` §9 and `TEST_PLAN.md` require, so later tasks add cases rather than infrastructure:

|---|---|---|

**Verify:** `test` passes without Docker; `test:integration` passes with Compose up and fails with a clear message when it is down.

## 9. Step 8 — CI (D10)

Pipeline on a clean checkout:

1. Install with the committed lockfile (frozen; fail on drift).
2. `typecheck`.
3. `lint` and `format:check`.
4. `test`.
5. Start PostgreSQL and Redis service containers, run `db:migrate:deploy`, then `test:integration`.
6. Build the three backend processes and the Docker images; run a production-like Compose smoke test asserting every readiness probe (`TECHNICAL_DESIGN.md` §10).

CI must never print secret values and must not require any credential beyond ephemeral local service containers.

**Verify:** CI green on a clean checkout; a deliberately broken type or lint rule fails the run.
