# BE-07 — Event Publish: Validation, Transaction, Idempotency

**Task (`IMPLEMENTATION_PLAN.md` §3):** event publish API with body/type/key-scope validation, DB transaction, delivery snapshots, idempotency fingerprint.
**Dependencies:** `BE-03`, `BE-04`, `BE-05`, `BE-06`.
**Blocked by:** **ADR-04** for the payload cap and rate limits — implement as configuration with the `PRD.md` §7 proposal (256 KiB) as the default, not as a hardcoded constant.
**Requirements:** `FR-EVT-01`..`08`, `FR-DEL-01`, `FR-APP-03`, `FR-KEY-04`, `FR-SEC-03`. Tests: `QA-E2E-02/03/08`, `QA-CON-01/02`, `QA-RES-01/02`, `AT-01`..`03`, `AT-08`, `AT-10`.

**Normative inputs:** `PRD.md` §3 F05 and §6; `API_SPECIFICATION.md` §3; `TECHNICAL_DESIGN.md` §3 (publish pseudocode and canonicalization); `SYSTEM_ARCHITECTURE.md` §4.2; `DATABASE_DESIGN.md` §5 (publish transaction).

This is the highest-risk correctness task in the backend. The dominant failure mode is returning `202` for state that is not durably committed.

## Scope boundary

In scope: `POST /v1/events` — authentication via the `BE-05` guard, validation, subscription matching, the single atomic transaction, idempotency arbitration, and the accepted response.

Out of scope: enqueueing to Redis (`BE-08` — the transaction writes outbox *rows* only), sending (`BE-09`), read APIs (`BE-11`).

## Implementation requirements

1. **Contract exactly as specified** (`API_SPECIFICATION.md` §3). Headers: `Authorization: Bearer flw_...`, mandatory `Idempotency-Key`, `Content-Type: application/json`. Body: `{ application_id, type, data }`. Response `202`: `{ id, status: "accepted", application_id, type, delivery_count, no_matching_reason, accepted_at }`.
2. **Validation before any write** (`FR-EVT-02`):
   - `application_id` required, exists, `ACTIVE`, owned by the principal's organization, and present in the key's allowlist — otherwise `403`/`404` per the contract, with no persistence (`FR-APP-03`, `FR-KEY-04`).
   - `type` required, matching `^[a-z][a-z0-9_.-]{0,99}$`.
   - `data` must be a JSON object in v0.1; reject other JSON values.
   - Combined body within the configured cap → `413` when exceeded (`FR-SEC-03`, ADR-04).
   - `Idempotency-Key` mandatory, 1–128 safe printable characters.
   - Rate limit per organization and credential → `429` with `Retry-After` when known.
3. **Request fingerprint.** SHA-256 over a deterministic canonicalization of the validated, typed request (`TECHNICAL_DESIGN.md` §3). Canonicalization must recursively sort object keys and explicitly define number normalization, string encoding and array handling. Two semantically identical requests must produce an identical fingerprint; two different payloads must not collide. Document the algorithm next to the implementation and pin it with fixtures — changing it later invalidates stored fingerprints.
4. **Subscription matching.** Resolve enabled endpoints under **that application only**, subscribed to that exact event type (`FR-END-05`, `FR-DEL-01`). No fan-out to another application, no wildcard topics, no cross-tenant match.
5. **One atomic transaction** (`DATABASE_DESIGN.md` §5, `TECHNICAL_DESIGN.md` §3). Inside it: resolve or insert the idempotency-bearing event row; create the immutable event; create one delivery per matched endpoint **snapshotting `target_url_snapshot` and `secret_version_id`**; create the first `outbox_message` per delivery with `attempt_number = 1`. Commit, then return `202` (`FR-EVT-03`, `FR-EVT-04`).
6. **Never acknowledge uncommitted state.** If the transaction cannot commit, return `5xx` and no `202`; a safe producer retry with the same key must then be possible (`FR-EVT-08`, `QA-RES-02`). Redis availability must play no part in acceptance (`NFR-01`, `QA-RES-01`).
7. **No external I/O inside the transaction.** No Redis call, no HTTP call, no DNS lookup. The dispatcher picks the work up asynchronously.
8. **Idempotency arbitration by the database.** Rely on unique `(organization_id, api_key_id, idempotency_key)`. On conflict, read the committed winner **after** the competing transaction resolves, compare fingerprints, and return either the original accepted response — optionally with `idempotent_replay: true` — or `409` with the stable conflict code (`FR-EVT-05/06`, `QA-CON-01/02`). Never use an in-process map for correctness.
9. **Zero subscribers.** Still `202`, with `delivery_count: 0` and `no_matching_reason: "no_matching_subscriptions"`. Create no delivery and no outbox row, and fabricate nothing (`FR-EVT-07`, `QA-E2E-03`).
10. **Response honesty.** `202` means durably accepted, never delivered. No field may suggest downstream success (`FR-EVT-04`, `QA-API-02`).
11. **Logging.** Structured, with `organization_id`, `event_id`, `request_id` and delivery count. Never the payload, the credential or the idempotency key's value where it could identify customer data (`FR-OBS-05`).

## Acceptance criteria

| # | Criterion | Test |
|---|---|---|
| 1 | One event to an application with two matching endpoints creates 1 event, 2 deliveries, 2 outbox intents, and `202` only after commit | `QA-E2E-02`, `AT-01` |
| 2 | 50 simultaneous identical publishes with one key produce exactly one event and a stable response | `QA-CON-01`, `AT-02` |
| 3 | Same key with a changed body returns `409` and creates no event | `QA-E2E-08`, `QA-CON-02`, `AT-03` |
| 4 | No matching subscription returns `202`, zero deliveries, `no_matching_subscriptions` | `QA-E2E-03`, `AT-01` |
| 5 | Key scoped to A1 publishing to A2 or B1 is denied with no persistence | `QA-AUTH-03`, `AT-08` |
| 6 | A disabled application or disabled endpoint produces no delivery to it | `FR-APP-03`, `FR-END-05` |
| 7 | Redis unavailable: publish still commits and returns `202`; outbox rows remain `PENDING` and dispatch after recovery | `QA-RES-01`, `AT-10` |
| 8 | Transaction failure returns no `202`; a retry with the same key succeeds without a ghost event | `QA-RES-02` |
| 9 | Over-cap body returns `413`; rate limit returns `429`; neither creates an event | `QA-SEC-09` |
| 10 | Deliveries carry the URL and secret-version snapshot taken at acceptance | `QA-E2E-10` |

## Tests

- **Unit:** validation matrix; canonicalization and fingerprint stability fixtures, including key-order, numeric-format and unicode variants; the "different payload must not collide" assertion; response shaping.
- **Integration (real PostgreSQL):** the full transaction; concurrent duplicate publishes via parallel connections; conflict path reading the committed winner; zero-subscriber path writing nothing; Redis stopped during publish.
- **Contract:** `QA-API-02` response schema; error envelope for `400`, `403`, `409`, `413`, `422`, `429`.
- **Security:** `QA-AUTH-03`, `QA-SEC-09`; a log-scan test asserting no payload or credential is logged.

## Definition of Done

`POST /v1/events` matches the contract exactly; validation rejects before persistence; one atomic transaction creates event, deliveries with snapshots, and first outbox intents; `202` is impossible without a commit; idempotency and conflict arbitrated by the database under real concurrency; zero-subscriber path honest; no external I/O inside the transaction; caps and limits configurable per ADR-04; all listed tests pass against real PostgreSQL.
