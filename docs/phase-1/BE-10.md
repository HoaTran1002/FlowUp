# BE-10 — Bounded Retry, Lease Recovery, UNKNOWN Attempts, Generation Guards

**Task (`IMPLEMENTATION_PLAN.md` §3):** bounded retry with persisted next due, lease expiry recovery, UNKNOWN attempts, generation guards.
**Dependencies:** `BE-09`.
**Blocked by:** **ADR-04** — retry schedule, max attempts, max retry age. Implement every value as configuration with the `PRD.md` §7 / `TECHNICAL_DESIGN.md` §5 proposals as defaults: 5 total attempts, base 5s, jitter in [0.8, 1.2], cap, 24h horizon, 10s timeout. Never hardcode; never present as final.
**Requirements:** `FR-RET-01`..`06`, `NFR-03`, `NFR-04`. Tests: `QA-E2E-06`, `QA-RES-04`, `QA-RES-06`, `QA-CON-03`, `AT-04`, `AT-05`.

**Normative inputs:** `TECHNICAL_DESIGN.md` §5 (retry schedule, lease recovery); `DATABASE_DESIGN.md` §4 state machines, §5 retry scheduling; `SYSTEM_ARCHITECTURE.md` §5 failure table; `apps/api/AGENTS.md` §5.

## Scope boundary

In scope: the retry scheduler that runs after an attempt result, the recovery path for expired leases and crashed workers, `UNKNOWN` attempt classification, generation guards, and terminal-failure determination.

Out of scope: performing an attempt (`BE-09`), enqueueing (`BE-08`), manual replay (`BE-12`). This task decides *whether and when* another attempt happens; the dispatcher decides when to hand it to the queue.

## Implementation requirements

1. **One scheduling transaction** (`DATABASE_DESIGN.md` §5). After an attempt result, in a single short transaction: finalize the attempt; set the delivery to `RETRY_WAIT` with `next_attempt_at`; increment `attempts_in_generation`; insert the next `outbox_message` with the incremented `attempt_number`. The Redis enqueue happens later, in the dispatcher, outside this transaction.
2. **Backoff.** `delay = min(cap, base * 2^(attemptNumber - 1)) * jitterFactor` with bounded jitter; attempt 1 is immediate (`TECHNICAL_DESIGN.md` §5). The computed due time is persisted in `delivery.next_attempt_at` — the database is the schedule, not a queue delay (`FR-RET-03`).
3. **Bounds.** Enforce `attempts_in_generation < max_attempts` **and** the retry horizon measured from delivery creation. Exceeding either ends the delivery in terminal `FAILED` with a recorded reason (`FR-RET-05`, `QA-E2E-06`).
4. **Terminal classification.** Permanent errors from `BE-09`'s classifier schedule nothing (`FR-RET-02`, `AT-05`). A terminal `FAILED` delivery becomes eligible for manual replay (`BE-12`) and for nothing else automatic.
5. **Lease expiry recovery.** A recovery path — reconciler or scheduled sweep — must find deliveries whose `lease_expires_at` has passed while still `IN_PROGRESS`, mark the stale `STARTED` attempt as **`UNKNOWN`** and immutable, and make the delivery due again if its budget allows (`DATABASE_DESIGN.md` §4, `TECHNICAL_DESIGN.md` §5).
6. **UNKNOWN semantics.** `UNKNOWN` means the outcome is genuinely unknowable: the worker may have sent the request and died before recording the response (`QA-RES-04`). Never record it as a confirmed failure, never as a success, and never overwrite it later. The next attempt may duplicate consumer processing — this is at-least-once and must be stated, not hidden (`NFR-03`, `FR-RET-06`).
7. **Generation guards.** Every conditional update carries the generation. A job or recovery action for a stale generation is a no-op. Prior attempts are never renumbered, rewritten or deleted (`QA-DB-03`, `FR-RET-06`).
8. **Cancellation races.** If the endpoint or application is disabled while a delivery waits, cancel the unsent delivery rather than scheduling another attempt (`FR-END-06`, `QA-CON-03`). A request already in flight may finish; do not claim otherwise.
9. **No second retry authority.** BullMQ jobs stay `attempts: 1`. The only retry engine is this scheduler plus the DB-owned due time (`apps/api/AGENTS.md` §5).
10. **Determinism in tests.** Make the clock and jitter injectable so the schedule is assertable (`TEST_PLAN.md` §2 deterministic clock).
11. **Observability.** Metrics for retry counts, retry-wait age, lease expiries and final failures; these feed the `BE-13` alerts (`SYSTEM_ARCHITECTURE.md` §7).

## Acceptance criteria

| # | Criterion | Test |
|---|---|---|
| 1 | A retryable failure sets `RETRY_WAIT` with a persisted next due time and exactly one next outbox intent | `QA-E2E-06` |
| 2 | Backoff grows exponentially within the cap and jitter band; attempt 1 is immediate | `FR-RET-03` |
| 3 | Exhausting max attempts or the retry horizon produces terminal `FAILED` | `QA-E2E-06`, `FR-RET-05` |
| 4 | A permanent error schedules no retry | `AT-05`, `QA-E2E-05` |
| 5 | A worker crash after a consumer 2xx but before the DB update leaves an `UNKNOWN` attempt and a coherent history; a possible duplicate is documented | `QA-RES-04`, `NFR-03` |
| 6 | A stale `STARTED` attempt past lease expiry becomes `UNKNOWN` and is never mutated again | `DATABASE_DESIGN.md` §4 |
| 7 | Concurrent workers on one job produce no overlapping active attempt in the same generation | `QA-RES-06` |
| 8 | Disabling during retry wait cancels instead of scheduling | `QA-CON-03` |
| 9 | A stale-generation job performs no state change | `FR-RET-06` |
| 10 | No BullMQ-level retry exists anywhere in the configuration | `TECHNICAL_DESIGN.md` §4 |

## Tests

- **Unit:** backoff and jitter with an injected clock; budget and horizon predicates; terminal-vs-retryable decisions; generation guard.
- **Integration:** attempt → schedule → dispatch → second attempt cycle; exhaustion to terminal `FAILED`; lease-expiry sweep producing `UNKNOWN`; concurrent claim; cancellation during retry wait; assertion that a replay later preserves these attempts.
- **Resilience:** `QA-RES-04`, `QA-RES-06` with a worker killed mid-request against a receiver that has already responded.

## Definition of Done

Retry scheduling is persisted in the database with bounded backoff, attempts and horizon, all configurable per ADR-04; terminal failures are correct and replay-eligible; expired leases recover with immutable `UNKNOWN` attempts; generation guards prevent stale writes; history is never rewritten; duplicate consumer receipt is documented rather than denied; no queue-level retry exists; listed tests pass with a deterministic clock.
