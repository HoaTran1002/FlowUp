# BE-04 — Applications CRUD and Disable Policy

**Task (`IMPLEMENTATION_PLAN.md` §3):** organization-scoped applications CRUD including disable with an explicit pending policy.
**Dependencies:** `BE-02`, `BE-03`.
**Blocked by:** **ADR-03** — the effect of disabling an application on pending deliveries is undecided. Implement the publish block (settled) and gate the pending-delivery effect behind the decision; do not invent it.
**Requirements:** `FR-APP-01`..`03`, `FR-SEC-01`, `FR-SEC-06`. Tests: `QA-E2E-01`, `QA-AUTH-02/03`.

**Normative inputs:** `PRD.md` §3 F03; `API_SPECIFICATION.md` §4 (applications); `DATABASE_DESIGN.md` §3; `SYSTEM_ARCHITECTURE.md` §4.1.

## Scope boundary

In scope: `POST /v1/applications`, `GET /v1/applications`, `PATCH /v1/applications/{id}`, and the application-status checks other modules consume.

Out of scope: endpoints (`BE-06`), key allowlists (`BE-05`), publish-time matching (`BE-07`), UI (`FE-03`). There is no delete route in v0.1 — disable is the lifecycle operation.

## Implementation requirements

1. **Routes exactly as specified** (`API_SPECIFICATION.md` §4): create accepts `{ "name": string }` and returns `201` with `{ id, name, status, created_at }`; list is cursor-paginated per §1; patch accepts `name` and `status` (`ACTIVE` | `DISABLED`) and returns `200`. No field or route beyond the contract.
2. **Tenant scoping.** Derive `organization_id` from the principal. Every read and write is organization-scoped; a non-owned ID returns `404` (`FR-SEC-01`, `QA-AUTH-02`).
3. **Roles.** Admin and Developer may both manage applications (`API_SPECIFICATION.md` §1). Enforce server-side.
4. **Recipient boundary semantics.** The application ID is the recipient boundary, independent of any human or legal customer identity (`FR-APP-02`). Do not add customer, tenant-of-tenant or contact fields — that is CRM scope and prohibited.
5. **Validation.** Name is required, trimmed, length-bounded, and stored as given. Reject unknown properties (`forbidNonWhitelisted`). Status transitions follow `ACTIVE ↔ DISABLED` (`DATABASE_DESIGN.md` §4); any other value is `422`.
6. **Disable — settled part.** A disabled application blocks new publishes: `BE-07` must reject an event targeting it (`FR-APP-03`). Expose a single reusable check so `BE-05` and `BE-07` do not duplicate the rule.
7. **Disable — ADR-03 part.** Whether disabling cancels already-pending deliveries is undecided. Implement the decision as an explicit, documented policy behind one named code path, and state in the response contract and the `FE-03` notes what actually happens. Do not silently assume cancellation, and do not leave the behavior undefined in the API documentation.
8. **Status consumers.** Provide the application-status read used by key scope validation and publish matching, so no module queries the table ad hoc with its own tenancy rules.
9. **Audit.** Create, rename and status change produce `audit_log` entries with actor, organization and the safe field delta (`FR-SEC-06`). No payloads, no secrets.

## Acceptance criteria

| # | Criterion | Requirement |
|---|---|---|
| 1 | Applications are created, listed and patched only within the principal's organization | `FR-APP-01`, `FR-SEC-01` |
| 2 | A cross-tenant application ID returns `404` on read and on patch, with no mutation | `QA-AUTH-02` |
| 3 | Listing uses cursor pagination with deterministic `(created_at, id)` ordering | `API_SPECIFICATION.md` §1 |
| 4 | A disabled application causes `BE-07` publish to be rejected | `FR-APP-03` |
| 5 | The pending-delivery effect of disabling is documented and matches implementation | ADR-03 |
| 6 | Invalid status or unknown property returns `422` without partial write | `FR-EVT-02` style validation |
| 7 | Mutations appear in the audit log with actor and organization | `FR-SEC-06` |
| 8 | No cross-application fan-out is possible through this API | `FR-APP-03` |

## Tests

- **Unit:** name validation; status transition guard; the reusable "application usable for publish" predicate.
- **Integration:** CRUD against PostgreSQL; cursor stability across pages with inserts between requests; audit row written per mutation.
- **Security:** cross-tenant read and patch (`QA-AUTH-02`); Developer and Admin both permitted, anonymous denied (`QA-AUTH-01`).
- **Cross-task:** a disabled application rejects publish — assert in `BE-07`'s suite, referenced here.

## Definition of Done

The three routes match the contract exactly; tenancy and roles enforced server-side; disable blocks publish; the ADR-03 pending-delivery policy is decided, implemented in one place and documented, or the task reports it as blocking; audit entries written; tests above pass; no delete route, no CRM-adjacent field added.
