# BE-05 — Producer API Keys: Create, Verify, Revoke

**Task (`IMPLEMENTATION_PLAN.md` §3):** API key creation/verify/revoke, hash and application allowlist, redacted metadata.
**Dependencies:** `BE-02`, `BE-03`, `BE-04`.
**Requirements:** `FR-KEY-01`..`04`, `FR-SEC-04`, `FR-SEC-06`. Tests: `QA-E2E-01`, `QA-E2E-11`, `QA-AUTH-03/04`, `QA-SEC-07`.

**Normative inputs:** `PRD.md` §3 F02; `API_SPECIFICATION.md` §1 and §4 (api-keys); `DATABASE_DESIGN.md` §3 (`api_key`, `api_key_application`), §7; `TECHNICAL_DESIGN.md` §7 (key generation and hashing); `SYSTEM_ARCHITECTURE.md` §6.

## Scope boundary

In scope: the three admin routes, key generation and hashing, the application allowlist with composite tenant integrity, the producer authentication guard used by `POST /v1/events`, and redacted metadata reads.

Out of scope: endpoint signing secrets (`BE-06` — a different credential with a different lifecycle), publish validation itself (`BE-07`), the UI one-time dialog (`FE-05`). Machine keys never authenticate a management route.

## Implementation requirements

1. **Routes exactly as specified** (`API_SPECIFICATION.md` §4):
   - `POST /v1/api-keys` with `{ "name", "application_ids": [...] }` → `201` `{ id, key, prefix, application_ids }`. The raw `key` appears **only here**.
   - `GET /v1/api-keys` → `200` metadata only: id, name, prefix, scoped application IDs, status, created and last-used timestamps. Never the raw key or the hash.
   - `POST /v1/api-keys/{id}/revoke` → `200` status. Revocation blocks future publishes; already-accepted deliveries continue (`FR-KEY-03`, `PRD.md` §6 edge case 10).
2. **Admin only.** Creation and revocation are Admin-only, enforced server-side; Developer receives `403` (`API_SPECIFICATION.md` §1, `QA-AUTH-05`).
3. **Key generation.** Cryptographic RNG, high entropy, prefixed `flw_` with an environment segment per the contract's example (`flw_live_...`). Store a lookup-friendly random key ID or prefix plus a hash resistant to offline guessing (`TECHNICAL_DESIGN.md` §7). Given high-entropy random keys, a fast keyed hash is acceptable **only** if documented; never store plaintext, never store a reversible representation (`FR-KEY-02`, `FR-SEC-04`).
4. **Allowlist integrity.** `api_key_application` rows must reference applications owned by the same organization, enforced by composite foreign keys (`DATABASE_DESIGN.md` §3). Reject creation naming a non-owned or non-existent application with `404`/`422` and no partial write. An empty allowlist is rejected — a key must name its permitted applications explicitly.
5. **Verification guard.** Provide the producer authentication guard that: parses the Bearer credential; looks up by prefix/key ID; verifies the hash in constant time; rejects `REVOKED` keys; resolves organization and the allowlist; and exposes the machine principal. Rejection happens **before any persistence** (`FR-KEY-04`). Invalid or revoked credential → `401`; valid credential publishing to an application outside its allowlist → `403` with no event or delivery created (`QA-AUTH-03`, `AT-08`).
6. **Last-used tracking.** Update `last_used_at` on successful authentication without turning every publish into a write contention point — a bounded-granularity update is acceptable and must be documented. Never record the credential value.
7. **Redaction.** The raw key must not appear in logs, error bodies, audit metadata, queue jobs, metrics labels, traces or test snapshots (`FR-OBS-05`, `QA-SEC-07`). Add an explicit test asserting absence after creation.
8. **Audit.** Creation and revocation produce `audit_log` entries with actor, organization, key ID and scoped application IDs — never the key or hash (`FR-SEC-06`).
9. **Rate limiting.** Failed producer authentication is rate-limited to bound credential-stuffing; return `429` with `Retry-After` when known. Coordinate the limiter with `BE-13`.

## Acceptance criteria

| # | Criterion | Requirement |
|---|---|---|
| 1 | Raw key is returned exactly once, at creation | `FR-KEY-02`, `QA-SEC-07` |
| 2 | `GET /v1/api-keys` never contains the key or hash | `FR-KEY-03` |
| 3 | A key scoped to A1 publishing to A2 or B1 is denied with no persistence and no dispatch | `FR-KEY-04`, `QA-AUTH-03`, `AT-08` |
| 4 | A revoked key cannot publish; deliveries accepted before revocation still proceed | `QA-E2E-11` |
| 5 | Developer cannot create or revoke a key | `QA-AUTH-05` |
| 6 | Creation naming a non-owned application fails with no key created | `FR-SEC-01` |
| 7 | Hash comparison is constant-time and the stored value is non-reversible | `FR-SEC-04` |
| 8 | No key value appears in any log, audit row, error body or test artifact | `QA-SEC-07` |

## Tests

- **Unit:** key generation entropy and format; hash verification including constant-time comparison; allowlist predicate; revoked-state rejection.
- **Integration:** create → authenticate → publish-scope check → revoke → authenticate again, against PostgreSQL; composite FK rejection for a cross-tenant application ID; `last_used_at` update.
- **Security:** `QA-AUTH-03/04/05`, `QA-SEC-07`; a log-scan test asserting the raw key is absent from captured log output.

## Definition of Done

Three routes matching the contract; Admin-only enforced; keys generated with a CSPRNG and stored hashed; allowlist enforced with composite tenant integrity; the producer guard rejects invalid, revoked and out-of-scope credentials before persistence; raw key revealed once and provably absent everywhere else; audit entries written; listed tests pass.
