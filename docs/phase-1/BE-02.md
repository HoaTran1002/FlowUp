# BE-02 — Dashboard Auth Contract Addendum, Organizations and RBAC

**Task (`IMPLEMENTATION_PLAN.md` §3):** define the human auth invitation/session/CSRF OpenAPI addendum and implement secure organization/RBAC.
**Dependencies:** `BE-01`, decision **ADR-01**.
**Blocked by:** **ADR-01** — the dashboard auth/session/invitation/CSRF contract does not exist in Phase 2. This task's first deliverable is the contract itself; implementation may not begin until it is approved.
**Requirements:** `FR-ORG-01`..`04`, `FR-SEC-01`, `FR-SEC-06`. Tests: `QA-AUTH-01`..`05`.

**Normative inputs:** `PRD.md` §3 F01; `API_SPECIFICATION.md` §1 (auth surfaces, status conventions, error envelope) and §7 (contract review blockers); `SYSTEM_ARCHITECTURE.md` §6; `DATABASE_DESIGN.md` §3 identity tables; `UI_UX_SPECIFICATION.md` §7.1.

## Scope boundary

In scope: the auth contract addendum; `organization`, `user`, `membership` schema usage; session handling; CSRF protection; role enforcement primitives; the authenticated-principal abstraction every later task consumes; audit entries for membership mutations.

Out of scope: applications (`BE-04`), API keys (`BE-05` — a *separate* authentication mode), any producer route, the dashboard UI (`FE-02`), public self-signup (post-MVP, `PRD.md` §9).

## Step 1 — Contract addendum (deliverable, must be approved first)

Produce an addendum to `docs/API_SPECIFICATION.md` covering sign-in, sign-out, session representation, session refresh or expiry semantics, invitation issue and acceptance, and the CSRF mechanism. It must specify, for each route: method, path, request and response schema, status codes, error codes in the shared catalog, and rate-limit exposure.

Constraints the addendum must satisfy:

- Invite-only onboarding (`FR-ORG-01`). The first organization and admin may be provisioned by an operator-managed invitation (`API_SPECIFICATION.md` §2), but dashboard login must still be secure.
- Session transport is a `Secure`, `HttpOnly`, `SameSite` cookie plus CSRF protection, or a documented equivalent (`API_SPECIFICATION.md` §1). A JavaScript-readable persistent bearer token is not acceptable by default (`apps/web/AGENTS.md` §1).
- Human session auth and producer machine-key auth are separate, non-interchangeable modes (`SYSTEM_ARCHITECTURE.md` §6).
- These routes are **not** part of the producer API and must not be presented as such.

Do not implement beyond this step until the addendum is approved. State the blocker and stop.

## Implementation requirements

1. **Schema use.** Use the identity tables from `DATABASE_DESIGN.md` §3 created in `BE-03`: `organization`, `user` (unique normalized email, never plaintext passwords), `membership` with unique `(organization_id, user_id)` and role `ADMIN` | `DEVELOPER`. If `BE-03` has not landed, coordinate rather than creating a parallel migration.
2. **Authenticated principal.** Provide one request-scoped principal exposing user ID, organization ID and role. Every later module resolves tenancy from it. No service may accept an `organization_id` argument sourced from request input (`FR-SEC-01`).
3. **Authorization.** Enforce the role matrix from `API_SPECIFICATION.md` §1: Admin manages credentials and memberships; Developer manages integrations, reads data and replays. Authorization is checked server-side on every operation — a hidden UI control is never the control (`FR-ORG-03`).
4. **Isolation responses.** Unauthenticated → `401`. Authenticated but insufficient role → `403`. Existing resource not owned by the principal's organization → `404`, with no distinction from a genuinely absent resource (`API_SPECIFICATION.md` §1, `QA-AUTH-02`).
5. **Session security.** Bind the session to the documented cookie attributes; rotate the session identifier on authentication; invalidate on sign-out; enforce absolute and idle expiry; reject state-changing requests failing CSRF validation. Never log a session identifier or CSRF token.
6. **Credential storage.** If the approved contract uses passwords, store a modern memory-hard hash with per-user salt; never store or log the plaintext. Invitation tokens are single-use, high-entropy, expiring, and stored hashed.
7. **Audit.** Record actor ID and organization ID for every mutating operation (`FR-ORG-04`), and an `audit_log` entry for membership and permission changes (`FR-SEC-06`). No secrets or payloads in `safe_metadata_json`.
8. **Rate limiting.** Apply a bounded attempt limit to sign-in and invitation acceptance; return `429` with `Retry-After` when known.

## Acceptance criteria

| # | Criterion | Requirement |
|---|---|---|
| 1 | Auth contract addendum approved and merged into `API_SPECIFICATION.md` before implementation | ADR-01 |
| 2 | A user can only access organizations they belong to | `FR-ORG-02` |
| 3 | Org A principal requesting an Org B resource ID receives `404`, no mutation, no existence leak | `QA-AUTH-02` |
| 4 | Developer attempting an Admin-only operation receives `403` server-side | `FR-ORG-03`, `QA-AUTH-05` |
| 5 | Anonymous request to any management route receives `401` with no data | `QA-AUTH-01` |
| 6 | Expired or invalid session is denied; protected data absent from the response | `QA-AUTH-04` |
| 7 | A state-changing request without valid CSRF protection is rejected | `QA-SEC-08` |
| 8 | Membership and permission mutations produce audit entries with actor and organization | `FR-ORG-04`, `FR-SEC-06` |

## Tests

- **Unit:** role policy decisions; principal resolution rejecting input-supplied tenant IDs; session expiry calculation; invitation token single-use.
- **Integration:** full sign-in → authenticated request → sign-out cycle against PostgreSQL; cross-tenant access matrix for every route existing at this point; CSRF rejection; brute-force limit.
- **Security:** `QA-AUTH-01`..`05`, `QA-SEC-08`; assert no session identifier, token or password appears in logs.

## Definition of Done

Contract addendum approved and documented; organizations, memberships and roles enforced server-side; `401`/`403`/`404` semantics exact; CSRF and session hardening in place; audit entries written; `QA-AUTH-01`..`05` pass; typecheck, lint and tests pass; migration (if any) committed; no credential or token in logs or tests. Report which parts of the addendum were newly decided and by whom.
