# FE-03 — Applications Screens and Integration Instructions

**Task (`IMPLEMENTATION_PLAN.md` §4):** applications list/create/edit/disable + recipient ID copy + integration instructions.
**Dependencies:** `BE-04`, `FE-01`, `FE-02`.
**Blocked by:** **ADR-03** for the disable warning's exact wording — the pending-delivery effect must match what `BE-04` implements. Do not assume cancellation.
**Requirements:** `UI-03`, `FR-APP-01`..`03`. Tests: `UX-AC-01` (application half), `QA-E2E-01`, `QA-UI-01`, `QA-UI-07`, `QA-AUTH-02`.

**Normative inputs:** `UI_UX_SPECIFICATION.md` §3 UI-03, §5; `API_SPECIFICATION.md` §4 (applications); `PRD.md` §3 F03.

## Scope boundary

In scope: `/app/applications` list, create and edit forms, disable confirmation, `/app/applications/:applicationId` detail with the application ID copy action and sample publish payload.

Out of scope: endpoints (`FE-04`), API keys (`FE-05`), events (`FE-06`). The sample publish snippet is documentation only — the dashboard never publishes an event.

## Implementation requirements

1. **Routes and data.** Use `GET/POST/PATCH /v1/applications` through the shared Axios client and TanStack Query, with the query-key factory from `FE-01`. Invalidate only the application list and the affected detail after a mutation (`apps/web/AGENTS.md` §6).
2. **List.** Name, status and created date, with cursor pagination and filters preserved in search parameters. No total count inferred from a page (`UI_UX_SPECIFICATION.md` §5).
3. **Create and edit.** Required name with inline validation, disabled/submitting state, and preserved non-secret form data when a request fails (`UI_UX_SPECIFICATION.md` §5). Validate with Zod aligned to the OpenAPI schema; the server stays authoritative. Add no field the contract does not define — in particular nothing resembling customer or contact data (`FR-APP-02`).
4. **Disable.** An explicit confirmation dialog for this destructive-by-consequence action (`QA-UI-07`). The copy must state the real effect: new publishes to this application are blocked, plus whatever the approved ADR-03 policy does to pending deliveries. If ADR-03 is unresolved, state only the settled part and report the gap — never invent a consequence.
5. **Detail.** Show the application ID with a copy action, status, created date, and a **sample publish payload** as escaped, read-only text: the `POST /v1/events` body and headers from `API_SPECIFICATION.md` §3 with an obviously fake key. Label it documentation, and state that producer keys belong server-side only (`UI_UX_SPECIFICATION.md` §5).
6. **States.** Loading, empty, success and error for list and detail; validation error for forms; `403` and `404` handled as `FE-02` established (`QA-UI-01`, `QA-UI-05`).
7. **Security.** Never render API-supplied HTML; escape every user-controlled string. Never place an identifier that is not needed into the URL, and never a secret (`apps/web/AGENTS.md` §4).
8. **Accessibility.** Labeled fields, focus moved to the first invalid field, keyboard-operable dialogs with clear cancel and confirm, status conveyed by text and not colour alone (`UI_UX_SPECIFICATION.md` §5).

## Tests

- **Unit:** form schema; query-key construction; mutation invalidation targets.
- **Component:** list with populated, empty, loading and error data; create and edit validation; disable dialog copy and keyboard operation; copy action.
- **Integration (mocked API):** create → list refresh; patch → detail refresh; `403` and `404` paths; cursor paging.

## Definition of Done

List, create, edit, disable and detail implemented against the documented contract with no invented field; all four states plus validation and permission errors render; the disable confirmation states the approved effect honestly; the application ID copies and the sample payload is safe, escaped documentation; cache invalidation is narrow; accessibility requirements met; listed tests pass.
