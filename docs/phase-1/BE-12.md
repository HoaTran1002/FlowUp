# BE-12 — Manual Replay with Operation Idempotency and Audit

**Task (`IMPLEMENTATION_PLAN.md` §3):** replay transaction + operation idempotency + audit + generation-aware queue.
**Dependencies:** `BE-10`, `BE-11`.
**Requirements:** `FR-REP-01`..`04`, `FR-SEC-06`, `NFR-03`. Tests: `QA-E2E-07`, `QA-CON-04`, `QA-CON-05`, `QA-CON-06`, `QA-SEC-10`, `AT-07`.

**Normative inputs:** `API_SPECIFICATION.md` §5 (replay); `PRD.md` §3 F09 and §6 edge case 8; `DATABASE_DESIGN.md` §5 replay; `SYSTEM_ARCHITECTURE.md` §4.4; `UI_UX_SPECIFICATION.md` §3 UI-09.

## Scope boundary

In scope: `POST /v1/deliveries/{id}/replay` — eligibility checks, the generation-incrementing transaction, operation idempotency storage, audit, and the new dispatch intent.

Out of scope: the confirmation UI (`FE-08`), automatic retry (`BE-10`), the attempt execution itself (`BE-09`). Replay never bypasses the worker's safety checks.

## Implementation requirements

1. **Contract exactly as specified** (`API_SPECIFICATION.md` §5). Request carries an `Idempotency-Key` for the operation and an optional `{ "reason": string }`. Success returns `202` `{ delivery_id, generation, status: "PENDING" }`. Return `409` with a stable error code when the delivery is active, succeeded, cancelled, the endpoint is disabled, or a conflicting operation exists; `403`/`404` for authorization and ownership.
2. **Eligibility.** Only a **final `FAILED`** delivery whose endpoint is `ENABLED` may be replayed (`FR-REP-01`). Replay attempted before final failure returns `409` and creates no generation (`QA-CON-04`).
3. **Authorization.** Admin and Developer may replay (`API_SPECIFICATION.md` §1). Cross-tenant ID returns `404`. An unauthorized replay is denied and appears in the audit trail only as an authorized-action record — do not log attacker-supplied content (`QA-SEC-10`).
4. **Transaction** (`DATABASE_DESIGN.md` §5): lock the delivery row; re-verify status and endpoint state; increment `generation`; reset `attempts_in_generation`; set the delivery due; insert the outbox intent for `attempt_number = 1` of the new generation; append the audit entry. **Preserve every prior attempt** (`FR-REP-02`).
5. **Operation idempotency.** Persist the replay operation key so retrying the exact same request returns the **prior scheduled generation** instead of scheduling another one (`API_SPECIFICATION.md` §5). Two concurrent submissions of the same key produce one new generation and either the idempotent response or the documented conflict (`FR-REP-03`, `QA-CON-05`). Scope the key per organization and actor, and rely on a database unique constraint — not in-process state.
6. **Race safety.** Replay must not race the worker or reconciler into two parallel generations for one delivery. Use the row lock plus generation guards so the timeline stays coherent (`QA-CON-06`). Never erase or renumber old attempts to make the new generation look clean.
7. **Queue awareness.** The new intent flows through the normal dispatcher path (`BE-08`) with a generation-aware deterministic job ID. Stale jobs from the previous generation become no-ops in the worker (`BE-09`).
8. **Identity preservation.** Replay reuses the original event and delivery IDs so consumers can deduplicate, and advertises the new generation in the outbound `FlowUp-Generation` header (`SYSTEM_ARCHITECTURE.md` §4.4, `API_SPECIFICATION.md` §6).
9. **Honest semantics.** `202` means scheduled, never delivered (`FR-REP-04`). The API documentation must state that replay can cause the consumer to reprocess the webhook.
10. **Audit.** Record actor, organization, delivery, new generation and the optional reason; never a payload or secret (`FR-SEC-06`).

## Acceptance criteria

| # | Criterion | Test |
|---|---|---|
| 1 | Replaying a final `FAILED` delivery returns `202`, increments the generation and schedules attempt 1 | `QA-E2E-07`, `AT-07` |
| 2 | Prior attempts remain visible and unmodified after replay | `FR-REP-02`, `QA-DB-03` |
| 3 | Replay before final failure returns `409` with no new generation | `QA-CON-04` |
| 4 | A disabled endpoint, succeeded or cancelled delivery returns `409` | `API_SPECIFICATION.md` §5 |
| 5 | The same operation key submitted twice yields one new generation | `QA-CON-05`, `FR-REP-03` |
| 6 | Replay racing the worker or reconciler produces no parallel conflicting generation | `QA-CON-06` |
| 7 | A cross-tenant delivery ID returns `404`; an unauthorized actor is denied | `QA-SEC-10`, `QA-AUTH-02` |
| 8 | The replayed send carries the original event and delivery IDs and the new generation header | `QA-API-04` |
| 9 | An audit entry records actor, reason and new generation | `FR-SEC-06` |
| 10 | The response never claims delivery occurred | `FR-REP-04` |

## Tests

- **Unit:** eligibility predicate across every delivery status and endpoint state; operation-key scoping; response shaping.
- **Integration:** replay transaction against PostgreSQL asserting generation increment, preserved attempts and exactly one new outbox intent; concurrent identical replays; replay racing a reconciler sweep; stale previous-generation job treated as a no-op.
- **Security:** `QA-SEC-10`, `QA-AUTH-02`.
- **E2E:** `QA-E2E-07` — fail a delivery permanently, restore the receiver, replay, observe a new attempt and intact history.

## Definition of Done

The replay route matches the contract; only final `FAILED` deliveries with enabled endpoints are eligible; the transaction increments the generation, preserves all history and creates exactly one new intent; operation idempotency is enforced by a database constraint and survives concurrent submissions; races with worker and reconciler cannot create parallel generations; audit entries written; `202` never implies delivery; listed tests pass.
