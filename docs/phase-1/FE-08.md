# FE-08 — Replay Confirmation, Operation Idempotency and Race UX

**Task (`IMPLEMENTATION_PLAN.md` §4):** replay confirmation, idempotency header per user action, status/race UX.
**Dependencies:** `BE-12`, `FE-07`.
**Requirements:** `UI-09`, `FR-REP-01`..`04`. Tests: `UX-AC-06`, `UX-AC-07`, `QA-E2E-07`, `QA-CON-05`, `QA-CON-06`, `QA-UI-07`.

**Normative inputs:** `UI_UX_SPECIFICATION.md` §3 UI-09 replay rules, §5; `API_SPECIFICATION.md` §5 (replay); `PRD.md` §3 F09 and §6 edge case 8.

## Scope boundary

In scope: the replay control on the delivery detail screen, its eligibility gating, the confirmation dialog, the per-action idempotency key, and the `202`, `409` and race outcomes.

Out of scope: the delivery and attempt rendering itself (`FE-07`), the replay transaction (`BE-12`).

## Implementation requirements

1. **Eligibility gating.** The replay control is available only for a final `FAILED` delivery whose endpoint is `ENABLED`, and only for a permitted role (`FR-REP-01`, `UI_UX_SPECIFICATION.md` §3). Client gating is UX; the server's `403`/`409` remains the authority. Disable rather than hide the control where explaining why is more useful, with the reason stated.
2. **Confirmation dialog (`QA-UI-07`).** Must warn that replay can cause the consumer to reprocess the webhook (`FR-REP-04`), accept an optional reason, and require explicit confirmation. No replay may be triggered by a single unconfirmed click.
3. **Operation idempotency.** Generate one unique `Idempotency-Key` per user action and send it with `POST /v1/deliveries/{id}/replay` (`API_SPECIFICATION.md` §5). The key must be stable across a retry of that same action and must not be regenerated on a re-render. Disable the submit control while in flight so a double click cannot produce two operations (`FR-REP-03`, `QA-CON-05`).
4. **`202` handling.** Treat it as **scheduled, not delivered** (`UX-AC-06`). Refetch the delivery and its attempts so the incremented generation and the preserved prior attempts become visible. Never show "replayed successfully" or any wording implying delivery, and never optimistically insert an attempt row (`UI_UX_SPECIFICATION.md` §5: action feedback must come from the API response).
5. **`409` handling (`UX-AC-07`).** Explain that the delivery state changed — it may be active, succeeded, cancelled, the endpoint may be disabled, or a conflicting operation may exist — and offer a refresh. If the server returns the prior scheduled generation for an identical operation, present that honestly as already scheduled rather than as a new replay. Never present a `409` as success (`QA-CON-06`).
6. **Other errors.** `403` renders access denied; `404` renders not-found; `429` shows the rate-limit message with retry guidance; `5xx` offers a safe retry of the same operation key (`QA-UI-05`).
7. **No automatic mutation retry.** TanStack Query must not auto-retry this mutation. A retry happens only on an explicit user action, reusing the same operation key (`apps/web/AGENTS.md` §6).
8. **Cache invalidation.** On `202`, invalidate this delivery, its attempts and the deliveries list — not the whole cache.
9. **Accessibility.** Dialog focus management, keyboard operation, clear cancel and confirm semantics, and an announced result.

## Tests

- **Unit:** eligibility predicate across every delivery status and endpoint state; idempotency key generation and stability across re-renders; in-flight disabling.
- **Component:** dialog copy and confirmation gating; `202` result rendering; `409` explanation and refresh; double-click prevention.
- **Integration (mocked API):** `202` → refetch showing generation increment and preserved attempts; `409` race path; repeated identical operation returning the prior generation; `429` and `5xx`.
- **E2E (in `FE-10`):** `QA-E2E-07` against real services.

## Definition of Done

Replay is correctly gated, confirmed with an accurate duplicate-processing warning, and submitted with one stable operation idempotency key per action with double-submit prevention; `202` is treated as scheduled and triggers a refetch showing the new generation and intact history; `409` and every other error state are explained honestly with safe recovery; no optimistic success and no automatic mutation retry; invalidation is narrow; listed tests pass.
