# BE-03 — Prisma Business Schema, Constraints, Indexes and Fixtures

**Task (`IMPLEMENTATION_PLAN.md` §3):** Prisma schema, constraints, indexes, secret versions, attempts, outbox and audit; migration fixtures.
**Dependencies:** `BE-01`.
**Blocked by:** nothing structural. **ADR-02** affects only whether `endpoint_secret_version` is used with a grace window or immediate cutover — model the table either way. **ADR-04** affects retention columns' *values*, not their presence.
**Requirements:** `FR-EVT-03`, `FR-EVT-05`, `FR-DEL-01`, `FR-OBS-*`. Tests: `QA-DB-01`..`04`.

**Normative inputs:** `DATABASE_DESIGN.md` in full — §3 tables, §4 state machines, §5 transactions, §6 indexes, §8 migration sequence. Also `TECHNICAL_DESIGN.md` §2 (centralized migrations).

## Scope boundary

In scope: the complete v0.1 schema, every unique and foreign-key constraint, indexes including partial indexes via raw SQL, enums matching the state machines, deterministic test fixtures, and a seed for local development.

Out of scope: business logic of any kind. No services, no controllers, no encryption implementation (`BE-06` owns secret encryption; this task only provides the columns). Do not add a table that no v0.1 requirement needs.

## Implementation requirements

1. **Migration sequence.** Follow `DATABASE_DESIGN.md` §8 in order: identity and application; API key and permissions; endpoint, subscription and signing-secret version; event, delivery, attempt, outbox, audit; then indexes and cleanup support. One migration per step keeps review tractable.
2. **Tables.** Implement exactly the tables and columns in `DATABASE_DESIGN.md` §3, including the **normative** `outbox_message` column list: `id`, `organization_id`, `delivery_id`, `generation`, `attempt_number`, `kind='DELIVER'`, `state` (`PENDING`|`CLAIMED`|`ENQUEUED`), `available_at`, `lease_until`, `claim_token`, `enqueue_attempts`, `enqueued_at`, `created_at`.
3. **Unique constraints — these are requirements, not optimizations:**
   - `membership (organization_id, user_id)`
   - `application (organization_id, id)`; `endpoint (organization_id, id)`
   - `api_key_application (api_key_id, application_id)` with composite FKs preventing cross-organization assignment
   - `endpoint_subscription (endpoint_id, event_type)`
   - `event (organization_id, api_key_id, idempotency_key)` — arbitrates concurrent duplicate publishes (`FR-EVT-05`)
   - `delivery (event_id, endpoint_id)` — at most one initial obligation (`FR-DEL-01`, `QA-DB-01`)
   - `delivery_attempt (delivery_id, generation, attempt_number)` (`QA-DB-03`)
   - `outbox_message (delivery_id, generation, attempt_number, kind)` (`QA-DB-02`)
4. **Per-attempt outbox.** `DATABASE_DESIGN.md` §3 is explicit: do **not** key retry intents on `(delivery_id, generation)` alone. `attempt_number` is part of the unique key.
5. **Enums.** Model the state machines in `DATABASE_DESIGN.md` §4 as database enums: application `ACTIVE|DISABLED`; endpoint `ENABLED|DISABLED`; api key `ACTIVE|REVOKED`; event `ACCEPTED`; delivery `PENDING|IN_PROGRESS|RETRY_WAIT|SUCCEEDED|FAILED|CANCELLED`; attempt `STARTED|SUCCEEDED|FAILED|UNKNOWN`.
6. **Tenant integrity.** Every business row carries `organization_id` directly or through a tenant-owned parent. Use composite foreign keys where the design allows, so a cross-tenant reference is impossible at the database level (`QA-DB-04`). Consider Postgres RLS only as later defense in depth, not as a substitute for application scoping.
7. **Indexes.** Create the indexes in `DATABASE_DESIGN.md` §6, including the partial indexes on `outbox_message (state, available_at)` filtered to `PENDING` and `(state, lease_until)` for reclaim. Partial indexes require a raw SQL migration in `infrastructure/migrations/` — inspect the generated SQL and commit it.
8. **Append-only intent.** No cascading delete of accepted events, deliveries or attempts while within retention (`DATABASE_DESIGN.md` §7). Retention columns (`event.retention_until`) exist now; the deletion job is `BE-13`.
9. **Secret columns.** `endpoint.signing_secret_ciphertext` and `signing_key_version`, plus `endpoint_secret_version(id, endpoint_id, version, ciphertext, created_at, expires_at)`, and `delivery.secret_version_id` for the snapshot. Columns only — no key handling here.
10. **Fixtures and seed.** Deterministic fixtures matching `TEST_PLAN.md` §2: Organization A with Admin, Developer, applications A1 and A2; Organization B with Admin and application B1; API keys scoped to A1 or B1; enabled and disabled endpoints with known subscriptions; secrets with known test vectors; **PII-free payloads**. Fixtures must contain no realistic credential and must be reusable by integration, security and E2E suites.

## Acceptance criteria

| # | Criterion | Test |
|---|---|---|
| 1 | Migrations apply cleanly to an empty database and are idempotent on re-run | — |
| 2 | A second `(event_id, endpoint_id)` delivery insert fails | `QA-DB-01` |
| 3 | A duplicate `(delivery_id, generation, attempt_number, kind)` outbox insert fails | `QA-DB-02` |
| 4 | A duplicate attempt number inside one generation fails; replay does not renumber history | `QA-DB-03` |
| 5 | A cross-tenant foreign key insert is rejected; no orphan rows reachable | `QA-DB-04` |
| 6 | Concurrent inserts with the same `(organization_id, api_key_id, idempotency_key)` yield exactly one winner | `QA-CON-01` |
| 7 | `FOR UPDATE SKIP LOCKED` claim against `outbox_message` selects each row once under concurrency | `BE-08` prerequisite |
| 8 | Partial indexes exist and are used by the dispatcher's due-row query plan | `DATABASE_DESIGN.md` §6 |
| 9 | Generated SQL reviewed and matches `DATABASE_DESIGN.md`; deviations reported before applying | `AGENTS.md` §7 |

## Tests

- **Integration (real PostgreSQL, not mocked):** every unique constraint proven by a failing duplicate insert; concurrency tests for the idempotency index and the outbox claim; FK rejection matrix; `EXPLAIN` assertions for the partial indexes.
- **Fixtures:** a test asserting the fixture set contains no value matching a credential-like pattern (`flw_`, long hex secrets).

## Definition of Done

All tables, enums, constraints and indexes from `DATABASE_DESIGN.md` exist with reviewed SQL; migrations committed in the centralized location and forward-safe; `QA-DB-01`..`04` pass against real PostgreSQL; fixtures deterministic and credential-free; any deviation from the design document explicitly reported with rationale. No business logic introduced.
